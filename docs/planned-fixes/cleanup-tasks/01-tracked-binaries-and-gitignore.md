# Cleanup — tracked binaries and missing `.gitignore`

Source: [`../../NEW_AUDIT.md`](../../NEW_AUDIT.md) Medium findings ("Committed
binaries doubled, not cleaned up" and "Working tree currently carries
uncommitted capture artifacts..."). Not a code bug — no TDD test suite applies;
this is a git/repository-hygiene action.

## Current state (verified at audit time, 2026-08-25)

- `git ls-files` shows six tracked compiled artifacts at the repository root:
  `monitor` (6.3 MB), `npm-ebpf-monitor` (7.6 MB), `exporter`, `labeler`,
  `validator`, and `coverage.out` — all ELF executables or build byproducts, not
  source.
- No `.gitignore` file exists anywhere under `src/npm-ebpf-monitor` (`ls
  .gitignore` → "No such file or directory").
- The working tree, independent of the above, currently shows
  `internal/collector/syscalltracer_x86_bpfel.o` and
  `internal/collector/tcpmonitor_x86_bpfel.o` as locally modified with **no**
  corresponding source change (`git diff --stat -- bpf/syscall_tracer.bpf.c
  bpf/tcp_monitor.bpf.c` is empty) — i.e. a local `go generate`/rebuild produced
  non-reproducible bytecode diffs against unchanged `.bpf.c` source. This is the
  live consequence of the drift risk `AUDIT.md` already named for committed
  `.o` files, observed actually occurring rather than only theorized.
- `npm-ebpf-monitor` itself (the binary, not the repo) also shows as locally
  modified, consistent with someone having run `make build` (which targets that
  exact name per the `Makefile`'s `BINARY_NAME`) since it was last committed.

## What this cleanup does **not** touch

`internal/collector/*_x86_bpfel.go` and their paired `.o` files
(`filemonitor_x86_bpfed.o`, `processtracer_x86_bpfel.o`, etc.) are a **prior,
defensible, and explicitly documented choice** (`AUDIT.md`'s own "Repo hygiene"
section: "a defensible choice for building without a BPF toolchain present").
This cleanup does not touch that decision or remove those files — only the full
compiled binaries and `coverage.out`, which have no equivalent justification.

## Plan

1. Add a `.gitignore` at `src/npm-ebpf-monitor/.gitignore` covering, at minimum:
   `/monitor`, `/npm-ebpf-monitor`, `/exporter`, `/labeler`, `/validator`,
   `coverage.out`, and `/report/` (the last already flagged in the original
   `AUDIT.md` as "currently untracked but unguarded"). Do **not** add a blanket
   `*.o` pattern — that would also match the intentionally-committed bpf2go
   outputs; scope it to the root-level binaries only (e.g. by path, not
   extension).
2. `git rm --cached monitor npm-ebpf-monitor exporter labeler validator
   coverage.out` (removes from tracking, leaves the local working files in
   place for anyone currently relying on them).
3. Confirm `make build`/the project's normal build flow still works
   post-removal — the binaries should simply become untracked build output
   again, not required to exist for anything else in the repo to function
   (verify: nothing under `scripts/`, `Makefile`, or `cmd/` reads a *committed*
   copy of these binaries; they're only ever build outputs or things a script
   invokes after building).
4. Leave the two currently-modified `.o` files (`syscalltracer_x86_bpfel.o`,
   `tcpmonitor_x86_bpfel.o`) as a decision point for whoever implements this:
   either commit the regenerated bytecode (if intentional and verified to match
   current `.bpf.c` source via a fresh `go generate`) or revert them to the
   last-committed version if the local rebuild was incidental to this audit
   session's own activity rather than a deliberate change. Do not silently pick
   one without checking which is correct.

## Verification

- `git status` shows no tracked binaries after the cleanup.
- A fresh `git clone` (or `git status` after `git rm --cached` + commit) confirms
  building the project still produces working binaries in the expected
  locations, just untracked.
- `git check-ignore -v monitor npm-ebpf-monitor exporter labeler validator
  coverage.out` confirms each is now correctly ignored.
